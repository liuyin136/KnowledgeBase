# v1.3 Embedding & Reranker Model Migration — Developer Guide

**Version**: 1.3
**Date**: 2026-07-04
**Status**: Implemented (default models migrated); this document is the **forward-looking guide** for adding a future embedding or reranker model.
**Audience**: DevOps / backend engineers extending the platform with a new embedding or reranker.

---

## 1. Overview

In v1.3 the platform's default embedding was migrated from `BAAI/bge-m3` to
`jinaai/jina-embeddings-v5-text-small`, and the default reranker was migrated
from `BAAI/bge-reranker-base` to `jinaai/jina-reranker-v3`. BGE-M3 and
BGE-reranker-base remain selectable via the `EMBEDDING_MODEL` / `RERANKER_MODEL`
environment variables (a runtime toggle, not a rebuild).

This document is the **guide for adding a FUTURE new embedding or reranker
model** to the platform. It enumerates the **4 primary code locations** that
must change for every new model, plus the secondary locations that need a
touch only when the model surface area changes meaningfully.

The v1.3 migration decisions (task conditioning, Matryoshka truncation,
`trust_remote_code`, float32 cast) are documented in §5 below as concrete
worked examples of the patterns described here.

---

## 2. The 4 Primary Code Locations

Adding a new embedding (or reranker) model always touches these four
locations. Each is described with its file path, what to change, and a
worked example.

### Location 1 — `backend/app/core/config.py`

**What this file owns**: Pydantic `Settings` (env-driven configuration) +
module-level lookup tables that map **logical model ids** (e.g.
`"jina-v5-small"`) to **HuggingFace repo ids** (e.g.
`jinaai/jina-embeddings-v5-text-small`) and **native output dims**.

**What to change for a new model**:

1. Add the new model's logical id → local-subdir-name mapping in
   `EMBEDDING_MODEL_IDS` (or `RERANKER_MODEL_IDS` for rerankers).
2. Add the new model's logical id → native-dim entry in `MODEL_NATIVE_DIM`
   (only if its native dim differs from 1024).
3. Add a `*_repo` field on `Settings` with the HuggingFace repo id default.
4. Extend the derived property `embedding_repo` (or `reranker_repo`) to
   resolve the new logical id → the new repo field.
5. Extend `embedding_model_name` (or `reranker_model_name`) to map the new
   logical id → the local subdir name (used to resolve a downloaded snapshot
   under `MODEL_PATH`).
6. Extend `reranker_max_length` if the new model is a reranker with a
   different max sequence length.
7. The Pydantic validators `_embedding_model_must_be_known` /
   `_reranker_model_must_be_known` automatically accept the new id once it
   is in the lookup table — no validator change needed.

**Example** — adding a hypothetical `e5-large-v2` embedding:

```python
# backend/app/core/config.py

EMBEDDING_MODEL_IDS = {
    "jina-v5-small": "jina-embeddings-v5-text-small",
    "bge-m3": "bge-m3",
    "e5-large-v2": "e5-large-v2",                 # NEW
}
MODEL_NATIVE_DIM = {
    "jina-v5-small": 1536,
    "bge-m3": 1024,
    "e5-large-v2": 1024,                          # NEW (native dim)
}

class Settings(BaseSettings):
    # ...existing fields...
    e5_large_v2_repo: str = Field(
        default="intfloat/e5-large-v2",
        description="HuggingFace repo id for E5 Large v2 (alternative embedding)",
    )

    @property
    def embedding_repo(self) -> str:
        if self.embedding_model == "bge-m3":
            return self.bge_m3_repo
        if self.embedding_model == "e5-large-v2":     # NEW branch
            return self.e5_large_v2_repo
        return self.jina_v5_repo

    @property
    def embedding_model_name(self) -> str:
        return EMBEDDING_MODEL_IDS.get(self.embedding_model, "jina-embeddings-v5-text-small")

    @property
    def model_dim(self) -> int:
        return MODEL_NATIVE_DIM.get(self.embedding_model, 1536)
```

> The Pydantic validator `_embedding_model_must_be_known` reads
> `EMBEDDING_MODEL_IDS` directly, so adding the new id to the dict
> automatically whitelists it — no validator body change needed.

### Location 2 — `backend/app/services/embedding.py`

**What this file owns**: `EmbeddingModule` — the singleton that loads the
active embedding model and produces vectors. STRICT module boundary: it
ONLY produces vectors. The orchestrator calls it.

**What to change for a new embedding**:

1. Add a **conditional branch in `load()`** for the new model — resolve the
   local snapshot dir (fall back to the HF repo id if not downloaded), then
   construct the `SentenceTransformer` with the model's specific kwargs:
   - `trust_remote_code=True` if the model ships a custom modeling file
     (Jina v5, Qwen3-embedding, etc.).
   - `truncate_dim=settings.embedding_dim` if the model is Matryoshka and
     its native dim > 1024 (so it writes into the existing 1024-dim Neo4j
     vector indexes — no index re-creation needed when switching models).
2. Add a **conditional branch in `embed_batch()`** for the new model's
   task / prompt handling:
   - Jina v5 needs `task="retrieval.query"` (when `is_query=True`) or
     `task="retrieval.passages"` (when `is_query=False`).
   - BGE-M3 ignores the `task` kwarg entirely.
   - A hypothetical new model may need a different prompt template (e.g.
     E5 requires `"query: ..."` / `"passage: ..."` prefixes — handle that
     by transforming the input text before calling `encode()`).

**Construction note #1 (MANDATORY — must be preserved on EVERY encode path
for EVERY model)**:

> After `model.encode(texts, ...)`, the output may be `bfloat16` on GPU.
> NumPy CANNOT handle `bfloat16` (no native dtype). ALWAYS cast:
>
> ```python
> emb_cpu = emb.detach().cpu().to(torch.float32)
> outputs.extend(emb_cpu.tolist())
> ```
>
> before returning any vector to callers. This is applied in `embed_batch`
> for both Jina v5 and BGE-M3 today, and MUST be applied for any new model
> too (Jina on GPU may also output `bfloat16`; E5 / Qwen3 / others can too
> when AMP autocast is active).

**Example** — adding the E5 branch (E5 is **not** Matryoshka and **not**
task-conditioned, but it **does** need input-text prefixes):

```python
# backend/app/services/embedding.py

# inside load():
if self._model_id == "jina-v5-small":
    self._model = SentenceTransformer(
        model_src, device=device,
        trust_remote_code=True,
        truncate_dim=settings.embedding_dim,
    )
elif self._model_id == "bge-m3":
    self._model = SentenceTransformer(model_src, device=device)
elif self._model_id == "e5-large-v2":
    # E5 is a vanilla transformer — no trust_remote_code, no Matryoshka
    # (it's natively 1024-dim). Load identically to BGE-M3.
    self._model = SentenceTransformer(model_src, device=device)
else:
    raise EmbeddingError(...)

# inside embed_batch(), per batch:
encode_kwargs = dict(
    batch_size=len(batch),
    convert_to_numpy=False,
    convert_to_tensor=True,
    normalize_embeddings=True,
    show_progress_bar=False,
)
if self._model_id == "jina-v5-small":
    encode_kwargs["task"] = JINA_TASK_QUERY if is_query else JINA_TASK_PASSAGE
elif self._model_id == "e5-large-v2":
    # E5 needs "query: " / "passage: " text prefixes — apply at the input
    # layer, NOT as an encode kwarg. Mutate the batch in place.
    prefix = "query: " if is_query else "passage: "
    batch = [prefix + t for t in batch]
# BGE-M3: no task / prefix kwargs — encode() defaults apply.

emb = self._model.encode(batch, **encode_kwargs)
# ─── Construction note #1 (MANDATORY — applies to ALL models) ─────────
# NumPy cannot handle bfloat16. Force the tensor to CPU + float32 before
# converting to a Python list. Jina on GPU, BGE-M3 on GPU, and E5 on GPU
# may ALL output bfloat16 under AMP autocast.
emb_cpu = emb.detach().cpu().to(torch.float32)
outputs.extend(emb_cpu.tolist())
```

> **For a new RERANKER**: this file is NOT touched. Rerankers live in
> `retrieval.py` (Location 3).

### Location 3 — `backend/app/services/retrieval.py`

**What this file owns**: `RetrievalModule` — hybrid search scoring + the
optional cross-encoder reranker (`_ensure_reranker` + `_rerank`). STRICT
module boundary: it ONLY scores. It NEVER embeds (the orchestrator embeds
the query and passes the vector + raw query text in).

**What to change for a new RERANKER**:

1. Add a branch in `_ensure_reranker()` for the new model — pass the
   resolved `model_src`, `max_length=settings.reranker_max_length`, and
   `trust_remote_code=True` only when the model ships a custom modeling
   file (Jina v3: yes; BGE-reranker-base: no).

**The `_rerank()` predict API is model-agnostic**:

> `CrossEncoder.predict(pairs, show_progress_bar=False)` works identically
> for every cross-encoder reranker. The only per-model differences are the
> repo id, max_length, and whether `trust_remote_code=True`. Once the model
> is loaded in `_ensure_reranker`, `_rerank` requires NO changes for a new
> reranker. Document this so a future maintainer doesn't try to "fix" it.

**Example** — adding a hypothetical `bge-reranker-v2-m3` branch:

```python
# backend/app/services/retrieval.py — _ensure_reranker()

local_path = os.path.join(settings.model_path, settings.reranker_model_name)
model_src = local_path if os.path.isdir(local_path) else settings.reranker_repo

# Models that ship a custom modeling file require trust_remote_code=True.
trust_remote = settings.reranker_model in {"jina-v3", "bge-reranker-v2-m3"}

self._reranker = CrossEncoder(
    model_src,
    device=settings.device,
    max_length=settings.reranker_max_length,   # NEW model's max_length from config.py
    trust_remote_code=trust_remote,
)

# _rerank() is UNCHANGED — CrossEncoder.predict() works for all rerankers.
# The float coercion `[float(s) for s in scores]` is also model-agnostic.
```

> **For a new EMBEDDING**: this file is NOT touched. Embeddings live in
> `embedding.py` (Location 2). (Retrieval uses the embedding through the
> orchestrator-supplied `query_vector`, never directly.)

### Location 4 — `backend/scripts/download_models.py` + `docker/Dockerfile.backend` model-download stage

**What these files own**: fetching model weights from HuggingFace Hub into
`MODEL_PATH/<repo-suffix>/` so the runtime stage can load them without
network calls at container start.

**What to change for a new model**:

1. In `backend/scripts/download_models.py`, append the new repo id to the
   `models` list (either always-download, or behind a new env-var toggle if
   the model is optional — see `DOWNLOAD_BGE` for the pattern).
2. In `docker/Dockerfile.backend` Stage 1 (`model-downloader`), the inline
   `MODELS` list mirrors `download_models.py`. Append the new repo id there
   too (or gate it behind the same env-var toggle if optional).
3. Document the **BuildKit cache mount benefit**: the
   `--mount=type=cache,target=/root/.cache/huggingface,sharing=locked`
   directive caches the HF hub download cache across rebuilds, so a
   code-only rebuild does NOT re-download multi-GB weights. A future model
   benefits from this automatically — no extra work needed.

**Example** — adding E5 to both download paths:

```python
# backend/scripts/download_models.py

models = [settings.jina_v5_repo]
if os.environ.get("DOWNLOAD_RERANKER", "1") == "1" and settings.enable_reranker:
    models.append(settings.jina_reranker_repo)

# Optional BGE toggle (existing v1.3).
if os.environ.get("DOWNLOAD_BGE", "0") == "1":
    models.append(settings.bge_m3_repo)
    if settings.enable_reranker:
        models.append(settings.bge_reranker_repo)

# NEW: always download E5 (it's a small ~1.3 GB model and a primary candidate).
# Or, gate behind a new DOWNLOAD_E5=1 toggle if it's optional.
if os.environ.get("DOWNLOAD_E5", "0") == "1":
    models.append(settings.e5_large_v2_repo)
```

```dockerfile
# docker/Dockerfile.backend — Stage 1 inline download script
RUN --mount=type=cache,target=/root/.cache/huggingface,sharing=locked \
    set -euo pipefail; \
    cat > /app/download_models.py <<'PY'
MODELS = [
    "jinaai/jina-embeddings-v5-text-small",
    "jinaai/jina-reranker-v3",
]
if os.environ.get("DOWNLOAD_BGE", "0") == "1":
    MODELS.extend(["BAAI/bge-m3", "BAAI/bge-reranker-base"])
# NEW: optional E5 download toggle.
if os.environ.get("DOWNLOAD_E5", "0") == "1":
    MODELS.append("intfloat/e5-large-v2")
PY
    DOWNLOAD_BGE=${DOWNLOAD_BGE} DOWNLOAD_E5=${DOWNLOAD_E5} python /app/download_models.py
```

> The `--mount=type=cache,target=/root/.cache/huggingface` cache mount is
> reused for the new model's weights — no per-model cache configuration
> needed.

## 3. Secondary Locations (mention, not deep-dive)

These locations are AWARE of the model selection but are mostly generic
and DO NOT require changes for a new model.

| File | What it does | Change needed for a new model? |
|---|---|---|
| `backend/app/api/v1/dashboard.py` | The `system` block reports `embeddingModel` / `embeddingModelLogical` / `embeddingNativeDim` / `rerankerModel` / `rerankerModelLogical` / `rerankerMaxLength`. **All fields are derived from `settings` dynamically** — no hardcoded model strings. | **No change needed.** The dashboard will automatically report the new model's repo id, native dim, and max_length once `config.py` resolves them. |
| `src/components/rag/views/settings-view.tsx` | The frontend Settings view is **read-only** and **generic** — it displays whatever the dashboard reports. | **No change needed for the data.** If you want to add a new option card (description, highlights) to the Embedding/Reranker Options section, append a card manually. The "How to Switch" section is text-based; update it if the switch instructions change. |
| `docker/docker-compose.yml` | Sets `EMBEDDING_MODEL` + `RERANKER_MODEL` env vars on the `backend` + `api-worker` services. | **No change needed** — the env var holds the *logical id*, which is validated by config.py. Once the new id is in `EMBEDDING_MODEL_IDS`, the compose file accepts it without modification. |
| `docker/.env.example` | Documents the selectable logical ids in inline comments. | **Update the comments** to list the new id (e.g. `# Embedding: jina-v5-small (default) \| bge-m3 \| e5-large-v2`). |
| `backend/app/services/orchestrator.py` | Calls `embed_with_retry(text, is_query=...)` on 4 sites (LongText window, ChildChunk parent, ChildChunk children, search query). The `is_query` flag is the only model-specific knob. | **No change needed** — the orchestrator passes `is_query` uniformly; `embedding.py` decides whether to use it (Jina: yes, BGE-M3: no, E5: yes via prefix). If a new model requires a fundamentally different call signature (e.g. a 3rd task type beyond query/passage), this file would need to thread a new parameter. |
| `backend/app/api/v1/dashboard/route.ts` (Next.js proxy) | Forwards the backend `system` block verbatim to the browser. When backend is offline, falls back to a v1.3 default. | **No change needed** unless you want the offline-fallback system block to name the new model as the default. |

## 4. Jina v5 Specifics (the v1.3 migration decisions)

This section documents the concrete decisions made when migrating the
default embedding to Jina v5. These are worked examples of the patterns
described in §2.

### 4.1 `task="retrieval"` (query vs passages)

Jina Embeddings v5 is **task-conditioned**: the same model produces
different vectors for a search query vs a document passage. The
orchestrator must tell the embedding module which role the input plays.

Implementation (`backend/app/services/embedding.py` `embed_batch`):

```python
if self._model_id == "jina-v5-small":
    encode_kwargs["task"] = JINA_TASK_QUERY if is_query else JINA_TASK_PASSAGE
```

Where `JINA_TASK_QUERY = "retrieval.query"` and `JINA_TASK_PASSAGE =
"retrieval.passages"` (constants in `app/core/constants.py`).

The orchestrator threads `is_query` through all 4 embed call sites:
- `ingest_long_text` per-window: `is_query=False` (documents → passages).
- `ingest_child_chunk` parent LongText: `is_query=False` (parent doc is a passage).
- `ingest_child_chunk` per-child: `is_query=False`.
- `run_search` query: `is_query=True` (query → `retrieval.query`).

BGE-M3 ignores the `task` kwarg entirely — the `is_query` flag is accepted
on every call but no-op for BGE-M3. This keeps the orchestrator call
signature uniform across models.

### 4.2 Matryoshka truncation to 1024

Jina v5 small natively outputs **1536-dim** vectors. The Neo4j vector
indexes (per `neo4j-schema-v1.1.md §3`) are **1024-dim cosine**. To keep
BOTH models writing into the SAME indexes (no index re-creation required
when switching), Jina is invoked with `truncate_dim=1024`:

```python
# backend/app/services/embedding.py — load()
self._model = SentenceTransformer(
    model_src,
    device=device,
    trust_remote_code=True,
    truncate_dim=settings.embedding_dim,   # 1024 — Matryoshka truncation
)
```

`truncate_dim` is the sentence-transformers knob for the Matryoshka
`dimensions=` parameter. It is set at **load time** (not at encode time)
because sentence-transformers' `encode()` does not accept `dimensions=`
directly — `truncate_dim` on the model is the supported knob.

BGE-M3 is natively 1024-dim, so no `truncate_dim` is passed for it. Both
models therefore emit 1024-dim vectors into the SAME Neo4j indexes.

> **Caveat**: vectors are still model-specific. Switching models requires
> **re-ingesting documents** so the persisted vectors match the active
> embedder. The Settings UI documents this clearly. The Neo4j vector
> indexes themselves do NOT need re-creation — only the `:KnowledgeChunk.vector`
> property values change.

### 4.3 `trust_remote_code=True`

Jina v5 ships a **custom modeling file** (not a standard
`sentence-transformers`-compatible `modeling_*.py`). Loading it requires
`trust_remote_code=True`, which tells the HuggingFace Hub + transformers
library to execute the remote modeling code from the repo.

BGE-M3 is a vanilla transformer — `trust_remote_code` is NOT set for it.

The same applies to rerankers: Jina Reranker v3 ships a custom modeling
file → `trust_remote_code=True`. BGE-reranker-base is a vanilla transformer
→ not set.

### 4.4 Float32 cast preserved (Construction note #1)

Jina on GPU may output `bfloat16` (under AMP autocast). NumPy has no
native `bfloat16` dtype and will raise a `TypeError` or return wrong values
via object arrays when downstream code (cosine similarity, `.tolist()`)
touches the raw tensor.

The cast `emb.detach().cpu().to(torch.float32)` is applied on EVERY encode
path for BOTH models — Jina v5 and BGE-M3 — with an explicit comment
marking the cast site. This pattern MUST be preserved for any future model.

```python
# ─── Construction note #1 (MANDATORY — applies to BOTH models) ──────
emb_cpu = emb.detach().cpu().to(torch.float32)
outputs.extend(emb_cpu.tolist())
```

## 5. Verification Checklist (for a DevOps engineer adding a new model)

After implementing the 4 primary code changes, run through this checklist:

- [ ] **config.py accepts the new model id**: `python -c "from app.core.config import Settings; s=Settings(embedding_model='e5-large-v2'); print(s.embedding_repo, s.model_dim)"` prints the expected repo + native dim without raising a validation error.
- [ ] **embedding.py loads the new model**: `python -c "from app.services.embedding import get_embedder; get_embedder().load()"` returns without `EmbeddingError`. Check the log line `embedding.load.ok` shows the new `model_id` + `model_src`.
- [ ] **`embed_batch` produces 1024-dim vectors**: `python -c "from app.services.embedding import get_embedder; e=get_embedder(); e.load(); v=e.embed('hello'); print(len(v))"` prints `1024` (or the model's native dim if it's natively 1024 — Jina uses Matryoshka truncation to 1024, BGE-M3 is natively 1024).
- [ ] **float32 cast present**: grep `embedding.py` for `torch.float32` — the cast must appear in `embed_batch` (and NOT be accidentally removed when adding the new model branch).
- [ ] **download_models.py fetches the new repo**: `python scripts/download_models.py` (with the appropriate `DOWNLOAD_*` env var if gated) prints `[download] <new-repo-id> -> /app/models/<name>` and completes without error.
- [ ] **Dockerfile.backend model-download stage includes the new repo**: grep `docker/Dockerfile.backend` for the new repo id (or for the new `DOWNLOAD_*` build arg if gated).
- [ ] **docker-compose.yml `EMBEDDING_MODEL` accepts the new id**: set `EMBEDDING_MODEL=e5-large-v2` in `.env`, then `docker compose up -d --force-recreate backend` — the container starts without a Pydantic validation error.
- [ ] **Dashboard system block reports the new model name**: `curl http://localhost:8000/api/v1/dashboard | jq .system.embeddingModel` returns the new repo id; `.system.embeddingModelLogical` returns the new logical id; `.system.embeddingNativeDim` returns the new native dim.
- [ ] **`python test_phase.py` (the verification script) passes**: run the platform's end-to-end verification script (ingest a sample doc → search → verify the result metadata). All assertions pass with the new model active.
