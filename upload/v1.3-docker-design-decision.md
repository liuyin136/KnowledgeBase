# ADR — v1.3 Docker Multi-Stage + BuildKit Cache Architecture

**Version**: 1.3
**Date**: 2026-07-04
**Status**: Accepted
**Supersedes**: v1.2 Dockerfile (single-stage model download + `nvidia/cuda:12.4.1-runtime-ubuntu22.04`)
**Companion docs**: `v1.3-embedding-migration.md` (model migration guide), `v1.3-powershell-commands.md` (Windows runbook)

---

## 1. Context

The Local-First RAG Experimentation Platform targets a heterogeneous
deployment:

- **Primary host**: Windows Docker Desktop (latest stable) with WSL2 backend,
  on a workstation with an NVIDIA GPU (GTX 3070 Ti, 8 GB VRAM).
- **Secondary host**: Linux servers with the NVIDIA Container Toolkit.
- **Incompatible**: Docker EE on Windows Server (without WSL2) does NOT
  support `--gpus all` natively — documented as a known limitation.

The backend image must run two workloads (FastAPI uvicorn + RQ api-worker,
same image, different CMD) and load BGE-M3 or Jina v5 embeddings on GPU.
The frontend image must serve the Next.js standalone build and proxy
`/api/v1/*` to the backend.

The backend image is **weight-heavy**: ~2-5 GB of model weights (Jina v5
small + Jina Reranker v3 by default, optionally BGE-M3 + BGE-reranker-base
via `DOWNLOAD_BGE=1`). Re-downloading these weights on every code change
is unacceptable for an iterative research workflow.

The v1.2 Dockerfile used `nvidia/cuda:12.4.1-runtime-ubuntu22.04` and
Ubuntu 22.04 (requiring the deadsnakes PPA for Python 3.12). The v1.3
directive specifies a CUDA 13.3 + Ubuntu 26.04 base and a `-devel-` flavor
to enable future source-built CUDA extensions.

---

## 2. Decision

Adopt a **2-stage multi-stage build** for the backend and **BuildKit cache
mounts** for the HuggingFace + pip caches.

### Backend — Stage 1: `model-downloader`

- **Base**: `python:3.12-slim` (minimal — no CUDA needed; the stage only
  issues HTTP calls to HuggingFace Hub).
- **Installs**: `huggingface_hub>=0.24,<0.30` + `git-lfs` (some repos store
  weights via LFS).
- **Download**: an inline Python script snapshots the configured repos
  (`jinaai/jina-embeddings-v5-text-small` + `jinaai/jina-reranker-v3` by
  default; `BAAI/bge-m3` + `BAAI/bge-reranker-base` when `DOWNLOAD_BGE=1`)
  into `/app/models/<repo-suffix>/`. Skips `.msgpack` / `.h5` / ONNX
  variants (only safetensors + tokenizer) to shave ~1.5 GB per model.
- **Cache mount**: `--mount=type=cache,target=/root/.cache/huggingface,sharing=locked`
  so the HF hub cache is reused across rebuilds.

### Backend — Stage 2: `runtime`

- **Base**: `nvidia/cuda:13.3.0-devel-ubuntu26.04` (per v1.3 directive).
- **Python**: 3.12 from apt (Ubuntu 26.04 ships 3.12 — no deadsnakes PPA
  needed; simpler than v1.2's Ubuntu 22.04 path).
- **System deps**: `build-essential`, `libgomp1`, `libgl1`, `libglib2.0-0`,
  `ca-certificates`, `curl`, `git`.
- **Pip install**: `--mount=type=cache,target=/root/.cache/pip,sharing=locked`
  for wheel cache reuse.
- **Copies**: models from Stage 1 (`COPY --from=model-downloader /app/models /app/models`)
  + backend code (`COPY . ./`, build context = `../backend`).
- **ENV**: `CUDA_VISIBLE_DEVICES=0`, `MODEL_PATH=/app/models`,
  `PYTHONPATH=/app`, `HF_HOME=/root/.cache/huggingface`.
- **CMD**: `uvicorn app.main:app --host 0.0.0.0 --port 8000` (overridden
  to `python -m app.workers.worker` for the `api-worker` service in compose).
- **Healthcheck**: `curl -fsS http://localhost:8000/health` every 15s.

### Frontend — 2-stage

- **Stage 1 `builder`** (`node:22-alpine` + bun 1.1.42): `bun install --frozen-lockfile`
  → `bun run build`. Sanity-check greps `next.config.*` for `output: 'standalone'`.
- **Stage 2 `runner`** (`node:22-alpine`): copies `.next/standalone` +
  `.next/static` + `public/`. `USER node` (non-root). `CMD ["node", "server.js"]`.

## 3. Rationale

- **Why multi-stage?** Separates the weight-download layer (slow,
  network-bound, ~2-5 GB) from the code layer. Code changes don't
  re-download weights. The final image excludes `git-lfs` + the download
  tooling — only the runtime deps + the model snapshots are baked in.

- **Why BuildKit cache mounts?** The HF hub cache (multi-GB) + the pip
  wheel cache are reused across builds. A code-only rebuild completes in
  **<60s** instead of re-downloading 5 GB of weights. Requires
  `DOCKER_BUILDKIT=1` (default in Docker Desktop ≥ 4.34 + Docker Engine
  ≥ 23.0). The cache mount survives `docker compose down` (it lives in
  the BuildKit cache, not in any container volume).

- **Why `nvidia/cuda:13.3.0-devel-ubuntu26.04`?** (v1.3 directive)
  - CUDA 13.3 is the latest stable. The driver-forward-compat model means
    a host driver ≥ the toolkit version is sufficient (no kernel-module
    install). On Windows Docker Desktop + WSL2, the driver is shared
    between Windows and WSL2 — install the latest NVIDIA Windows driver.
  - The **`-devel-`** flavor (vs `-runtime-`) is chosen so future
    source-built CUDA extensions (flash-attention, custom kernels, xformers
    source builds) compile without a base-image swap. **Trade-off**: the
    image is ~2 GB larger than `-runtime-`. This is acceptable for a GPU
    research workstation; it would be reconsidered for a fleet deployment.
  - Ubuntu 26.04 ships Python 3.12 in apt (no deadsnakes PPA) — simpler
    than v1.2's Ubuntu 22.04 + deadsnakes path, fewer apt repos to
    configure, smaller attack surface.

- **Why `python:3.12-slim` for Stage 1?** Minimal image for the download
  step. No CUDA needed (just `huggingface_hub` HTTP calls). Keeps the
  download stage fast + cacheable independently of the runtime stage — a
  weights-only change (e.g. `DOWNLOAD_BGE=1` flip) doesn't invalidate the
  runtime stage's pip cache.

- **Why standalone output for the frontend?** Next.js standalone bundles
  only the needed `node_modules` + `server.js` → final image is ~150 MB
  (vs ~1 GB if copying the full `node_modules`). `next.config.ts` already
  has `output: "standalone"`; the Dockerfile sanity-checks this and fails
  the build loudly if it's missing.

- **Why `PYTHONPATH=/app`?** So developers can run
  `docker compose exec backend python scripts/init_neo4j.py` (or any `.py`
  under `scripts/`) without passing `PYTHONPATH` each time. The
  `scripts/*.py` files import from `app.*` (e.g. `from app.core.config
  import settings`), which only resolves when `/app` is on the path.
  Without this, every `docker compose exec backend python scripts/...`
  command would need `env PYTHONPATH=/app python scripts/...`.

## 4. Trade-offs / Consequences

| Aspect | Assessment |
|---|---|
| **(+) Fast incremental rebuilds** | Code-only rebuild < 60s — the BuildKit cache mount on `/root/.cache/huggingface` keeps the multi-GB HF cache hot. |
| **(+) Small final frontend image** | ~150 MB standalone (vs ~1 GB with full `node_modules`). |
| **(+) Forward-compatible** | The `-devel-` base allows future CUDA kernel compilation without a base-image swap. |
| **(+) PYTHONPATH ergonomics** | `docker compose exec backend python scripts/...` "just works". |
| **(−) Backend image is large** | ~6 GB with `-devel-` + Jina + (optional) BGE weights. Acceptable for a single GPU research workstation; would be a concern at fleet scale. |
| **(−) BuildKit required** | Old Docker versions (< 23.0 Engine / < 4.34 Desktop) need `DOCKER_BUILDKIT=1` env var explicitly. Documented in `docker/README.md` + the PowerShell runbook. |
| **(−) Windows Docker Desktop + WSL2 GPU constraint** | GPU passthrough requires NVIDIA Windows driver + WSL2 GPU support. Docker EE on Windows Server (without WSL2) does NOT support `--gpus all` natively — documented in `docker/README.md`. |
| **(−) Inline download script duplicated** | The model-download logic lives both in `backend/scripts/download_models.py` (runtime, operator-runnable) and inline in the Dockerfile Stage 1 (build-time). They must be kept in sync when a new model is added. (Documented in `v1.3-embedding-migration.md` Location 4.) |

## 5. Alternatives Considered

| Alternative | Verdict | Reason |
|---|---|---|
| **Single-stage Dockerfile** (download weights + install deps + copy code in one stage) | Rejected | Re-downloads weights on every code change. Unusable iteration speed. |
| **Download weights at runtime** (entrypoint script on container start) | Rejected | Slow container start (minutes for a fresh download), no build caching, network failures at runtime cause the container to never become healthy. |
| **`-runtime-` base** (instead of `-devel-`) | Rejected for v1.3 | Would require a base-image swap if a future model needs kernel compilation (flash-attention, xformers source builds). The 2 GB size penalty is acceptable. |
| **Conda-based image** (`continuumio/miniconda3`) | Rejected | Heavier + slower than pip + apt. Conda's solver is non-deterministic across hosts. The platform's `requirements.txt` is pure pip — switching to conda would require re-pinning every dependency. |
| **Pre-built model wheel** (publish model weights as a pip-installable package) | Rejected | Most embedding models are NOT published as wheels (HuggingFace Hub is the canonical source). Wrapping them in a wheel would add maintenance burden for no benefit. |
| **Mount model dir as a Docker volume** (host downloads weights, mounts into container) | Rejected as default; allowed for dev | Works for dev iteration but breaks the "one-command reproducible deployment" goal. Documented as a dev-only override in the PowerShell runbook. |

## 6. Verification Checklist

After implementing or modifying the Dockerfile, run through this checklist:

- [ ] **`docker compose build backend` succeeds with BuildKit**: `docker compose build backend` completes without errors. (BuildKit is default in Docker Desktop ≥ 4.34 + Docker Engine ≥ 23.0; verify in Docker Desktop Settings → Build → "BuildKit enabled".)
- [ ] **HF cache mount is hit on rebuild**: `docker buildx build --progress=plain` output shows `CACHED` on the download layer when re-running a build with no weight changes. (First build downloads ~5 GB; subsequent code-only builds skip the download entirely.)
- [ ] **pip cache mount is hit on rebuild**: `docker buildx build --progress=plain` output shows `CACHED` on the `pip install -r requirements.txt` layer when `requirements.txt` is unchanged.
- [ ] **`nvidia-smi` works inside the container**: `docker compose exec backend nvidia-smi` prints the GPU info (confirms GPU passthrough).
- [ ] **`torch.cuda.is_available()` returns True**: `docker compose exec backend python -c "import torch; print(torch.cuda.is_available())"` prints `True` (confirms PyTorch sees the GPU through the CUDA base image).
- [ ] **PYTHONPATH works**: `docker compose exec backend python scripts/init_neo4j.py` runs without an `ImportError` / `ModuleNotFoundError` on `app.*` (confirms `/app` is on `sys.path`).
- [ ] **Model snapshot is present**: `docker compose exec backend ls /app/models` lists the expected subdirs (`jina-embeddings-v5-text-small`, `jina-reranker-v3`, and optionally `bge-m3` + `bge-reranker-base` when built with `DOWNLOAD_BGE=1`).
- [ ] **Frontend standalone image is small**: `docker images raglab-frontend --format "{{.Size}}"` reports ~150-200 MB (confirms the standalone output is being used, not the full `node_modules`).
- [ ] **Healthcheck passes**: `docker compose ps` shows `backend` as `(healthy)` within 60s of `docker compose up -d` (confirms the `curl /health` healthcheck works).
- [ ] **Worker boots**: `docker compose logs api-worker` shows the RQ worker starting up + connecting to Redis without errors (confirms the image's default CMD override works).
